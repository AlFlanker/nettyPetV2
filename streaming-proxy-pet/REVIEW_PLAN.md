## P-00. Вернуть транспорт на прямой io.netty — P1, архитектурное требование

**Владельцы:** Netty + техлид; Jetty проверяет servlet bridge. **Статус:** несоответствие подтверждено исходниками и уточнением пользователя.

**Код:** `build.gradle:17`; PET `ProxyTransport.java:6–7`, `:17–27`; `ProxyCommand.java:39–75`. В исходнике `ProxyCommand`, `ChannelManager`, `ProxyChannelInitializer` и `BackendResponseHandler` работают с Netty Channel/pipeline непосредственно.

**Целевая схема:**

```text
Jetty / HttpServletRequest
  → ProxyServlet / AsyncContext
  → ProxyCommand / единое состояние exchange
  → Netty Channel с HttpClientCodec, без HttpObjectAggregator
       DefaultHttpRequest: только метод, raw URI, заголовки
       HttpContent: очередная порция исходного тела
       LastHttpContent: корректный EOF
  → backend

backend HttpResponse + HttpContent + LastHttpContent
  → ограниченный writer / готовность Jetty
  → HttpServletResponse
```

**Действия:**

1. Заменить Reactor Netty HttpClient/ConnectionProvider прямым транспортом: общие EventLoopGroup/Bootstrap и минимальные channel/response handlers, близкие к исходному примеру. Удалить Reactor Netty зависимости; оставить нужные io.netty модули и при необходимости reactor-core.
2. Создавать один `DefaultHttpRequest` только для head. Servlet request и Netty request — разные объекты разных соединений, поэтому адаптация метода/URI/headers неизбежна. Требование «без пересоздания руками» трактуется как отсутствие повторной сборки тела, параметров и multipart, а не отсутствие исходящего HTTP head.
3. Передавать исходное тело через `HttpContent` порциями, завершать `LastHttpContent` только при нормальном EOF. Запретить `FullHttpRequest`, `HttpObjectAggregator`, `HttpPostRequestEncoder`, `getParameterMap()` и накопление всего тела на этом пути.
4. Связать запуск следующего servlet read с доступностью backend channel и ограничением незавершённых writes. `isWritable()` само по себе не ограничивает уже поставленные read/write задачи. Блокирующие servlet операции выполнять вне event loop; состояние обмена и порядок writes сериализовать.
5. На ответе связать Netty read demand с подтверждённой обработкой очередной порции writer. `AUTO_READ=false` само по себе не означает один HttpContent: codec может декодировать несколько объектов за read. Рассмотреть `FlowControlHandler` вместе с receive/decoder bounds; очередь уже декодированных объектов должна иметь явный предел и ownership.
6. Завершение write future означает завершение передачи владения соответствующему этапу, не даёт права повторно освобождать уже переданный outbound объект. Отмена, ошибки и завершение канала должны иметь явные правила release; объединить с P-03/P-04/P-05.
7. Не разрабатывать весь исходный ChannelManager заново. Для первого корректного pet допустимо отдельное backend-соединение на обмен с ограничением concurrency. Повторное использование соединений добавлять только с правилом: полностью завершённый ответ, отсутствие in-flight I/O и сброс состояния handler; повреждённые/отменённые каналы не возвращать в reuse.
8. Сохранять один обмен на канал без pipelining, отсутствие автоматических retry/redirect и распаковки payload. Для HTTPS явно настроить SslHandler с проверкой доверия и имени backend; закрывать собственные каналы/EventLoopGroup при остановке Spring-контекста.
9. Защитить обмен от поздних callbacks: чанк, дочитанный worker после cancel/early response, освобождается и не отправляется в следующий exchange. Ошибка передачи задачи в event loop также должна освобождать ещё не переданный буфер. Таймеры отменяются при terminal cleanup.
10. Проверять фактическую длину при известном CL; premature EOF не исправлять уменьшением CL и не обозначать успешным LastHttpContent. При раннем backend response определить ограниченный drain или close оставшегося клиентского тела; нечистый канал исключить из reuse.

**Приёмка:** runtime classpath и приложение не используют Reactor Netty; исходящий HTTP проходит через прямые Netty codec/handlers; тело любых поддержанных методов не агрегируется и не перекодируется; существующие и новые регрессии проходят. В тестах проверяются фактические границы очередей, ByteBuf ownership и корректный EOF, а не только наличие HttpContent в коде.

## P-01. Устранить скрытую агрегацию при замене транспорта и согласовать framing — P1

**Владельцы:** Netty + техлид. **Статус:** дефект воспроизведён.

**Код:** PET `ProxyCommand.java:46–49`; описание одинаковой передачи методов и ограниченности памяти в README.

`HttpClientOperations.send(Publisher)` в Reactor Netty 1.3.0 собирает тела GET/HEAD/DELETE в список. Наличие `Flux<ByteBuf>` у приложения само по себе не гарантирует потоковую передачу. DELETE с большим телом полностью удерживается в памяти и не начинает отправку до EOF.

**Действия:**

1. Зафиксировать контракт методов с телом: DELETE должен передаваться потоком; для GET/HEAD явно выбрать поддержку либо документированный отказ. Не оставлять неявную зависимость от поведения библиотеки.
2. В целевом решении выполнить P-00: прямой Netty head + поток HttpContent без агрегатора и без особой буферизующей ветки GET/HEAD/DELETE. Исправление Reactor Netty API больше не является направлением реализации.
3. Одновременно определить исходящий framing: известная длина, неизвестная длина, отсутствие тела. Не пересылать входящий `Transfer-Encoding` как end-to-end заголовок; формировать framing для нового соединения и исключить противоречивые CL/TE.
4. Сохранить диагностический результат прежнего прототипа: одна замена Reactor Netty send для unknown-length GET/DELETE приводила к 200 при нуле прочитанных backend байтов, потому что chunked не выставлялся. Это подтверждает необходимость явного контракта framing при переносе на прямой Netty. Сам прототип не переносится в целевую реализацию.
5. Выбрать Netty write/flush policy, обеспечивающую отправку первых порций до EOF и ограниченную очередь. Не ждать конца большого запроса ради единственного flush и не принимать flush-per-chunk за доказанную оптимальную стратегию.
6. После тестов исправить README: обещать только подтверждённый контракт.

**Приёмка:** параметризованные POST/PUT/PATCH/DELETE и выбранная политика GET/HEAD; Content-Length и chunked; пустое тело; backend получает первый чанк до разрешения EOF; совпадают длина и SHA-256; отсутствуют одновременно CL и TE; запрос не повторяется после ошибки. Для HEAD наблюдать получение request body на backend, не ожидать response body.

## P-02. Исключить проксирование локальных ERROR-dispatch — P1

**Владельцы:** Spring + Jetty. **Статус:** дефект воспроизведён.

**Код:** PET `ProxyApplication.java:23`, `ProxyServlet.java:24`, `:29–36`.

Servlet mapping `/*` перехватывает Boot `/error` раньше MVC DispatcherServlet с mapping `/`. Если слот освобождается между отказом 503 и ERROR-dispatch, ошибка принимается за новый proxy exchange. Полученный от backend статус заменяет локальный отказ.

**Действия:**

1. Формировать локальные 501/503 через `setStatus` и явное завершение выбранного тела/длины, без запуска error-page dispatch через `sendError`.
2. Добавить явный контракт `DispatcherType.ERROR`: такая диспетчеризация не должна создавать upstream exchange.
3. Не сломать отдельный ASYNC-dispatch, который сейчас используется при поздней ошибке после commit; согласовать его с P-03.
4. Определить принадлежность `/error` и других локальных путей: клиентский обычный REQUEST и внутренний ERROR — разные случаи.

**Приёмка:** управляемый тест освобождает capacity перед ERROR-dispatch отклонённого запроса; итог остаётся 503, backend не получает ни исходный отклонённый запрос, ни внутренний `/error`. Проверить 501, повторные отказы, отсутствие рекурсивных отправок и возврат capacity.

## P-03. Ввести единое владение ответом и терминальными действиями — P1

**Владельцы:** техлид + Jetty + Netty. **Статус:** конкурентные пути подтверждены кодом; конкретное повреждение ответа экспериментально не воспроизведено.

**Код:** PET `ProxyCommand.java:50–79`, `:82–90`, `ProxyServlet.java:63–72`; REF `proxy/ResponseOwnership.java:6–10`, `:31–33`.

Заголовки меняет callback Netty, тело пишет задача virtual thread, общий timeout запускает другую задачу `fail()`. Проверка `isCommitted()` перед `reset()` не атомарна. Отмена подписки не означает, что уже выполняющийся блокирующий servlet write завершился. Исходный пример специально содержит арбитраж `ResponseOwnership`, который при упрощении был потерян.

**Действия:**

1. Описать минимальные состояния exchange и единственного владельца ответа: normal/fallback/abort/terminal.
2. Сериализовать изменение статуса, заголовков, начало записи и терминальные действия. Одного флага или переноса всех операций на общий многопоточный scheduler недостаточно.
3. После захвата ответа backend-веткой определить допустимую обработку ошибки; после commit разрешать abort, а не reset или дописывание fallback.
4. Согласовать отмену upstream, активную запись, AsyncContext completion/dispatch и cleanup. Не переносить весь resilience-слой исходного модуля.
5. В прямом Netty варианте P-00 привязать эту модель к ChannelFuture/handler callbacks и одному владельцу состояния; наличие `Mono` вокруг команды само по себе не сериализует эти callbacks.

**Приёмка:** барьерами воспроизвести timeout непосредственно перед первым commit, одновременно с первым чанком и во время заблокированной записи. Допустим ровно один определённый исход; нет смешения статуса/заголовков/тела, записи после terminal, повторного complete/reset и ошибок ref-count.

## P-04. Проверять завершение реального I/O, а не только возврат semaphore — P2

**Владельцы:** Jetty + Netty. **Статус:** установлен пробел гарантии и тестирования; новая утечка потоков/соединений не доказана.

**Код:** PET `ProxyServlet.java:48–67`, `ProxyCommandSupport.java:26–39`, `ProxyCommand.java:62–79`, `ProxyTransport.java:40–46`; TEST `:59–61`, `:158–180`.

`doFinally` возвращает permit при завершении/cancel publisher. Это не подтверждение завершения блокирующего I/O, закрытия socket или AsyncContext. Прежняя утечка самого permit уже исправлена; нельзя выдавать её за новую находку.

**Действия:**

1. Определить, что именно ограничивает 32: логические exchanges или фактически активные I/O задачи. Не объявлять это абсолютным лимитом сокетов/памяти процесса.
2. Добавить наблюдение за завершением read/write задач и состоянием backend-соединений в тестах.
3. Проверить stalled upload без RST, медленного и переставшего читать downstream, FIN/RST, общий timeout, ранний backend 413 при незавершённом upload, shutdown с активными exchanges.
4. Если обнаружено отставание реального cleanup от выдачи capacity — согласовать освобождение ресурса с завершением I/O либо ввести отдельный ограничитель I/O. Возможный явный Jetty abort или ReadListener/WriteListener выбирать по результату, а не вводить заранее.

**Приёмка:** повторные волны отмен не увеличивают число живых read/write задач, занятых соединений и удержанных буферов; backend получает закрытие/корректное завершение; здоровые запросы продолжают работать. Cleanup остаётся идемпотентным.

## P-05. Усилить доказательства backpressure и владения ByteBuf — P2

**Владельцы:** Netty + техлид. **Статус:** пробел тестирования; double-release или утечка в текущей цепочке retain/release не обнаружены.

**Код:** PET `ProxyCommandSupport.java:20–39`, `ProxyCommand.java:62–74`; TEST `:109–155`; `build.gradle:35`.

Тест 16 MiB доказывает начало forwarding до EOF, но прошёл бы и вариант «передать первую порцию, затем накопить остаток». PARANOID без адресного учёта буферов и подходящих условий обнаружения не доказывает отсутствие утечек.

**Действия:**

1. Добавить slow-backend и slow-client сценарии с объёмом больше сетевых буферов: producer должен остановиться до EOF, когда потребитель перестал читать.
2. Измерять/ограничивать read-ahead с учётом transport queues и socket buffers; не требовать ровно одного чанка во всей системе только из-за `prefetch=1`.
3. Адресно проверить ref-count для очереди при cancel, исключении writer, early response и ошибке sender; использовать tracking allocator/test fixture там, где это возможно.
4. Сохранять текущий явный переход ownership: отправленный request buffer принадлежит Netty, response buffer удерживается при переходе scheduler и освобождается после записи/discard.

**Приёмка:** заведомо агрегирующая или продолжающая читать без ограничения версия проваливает тест; данные остаются побайтно верными; удержанные тестовые буферы освобождаются. Отдельно измерять память процесса, если в README потребуется количественная гарантия RSS/direct-memory.

## P-06. Ужесточить проверки обрыва и расширить HTTP-матрицу — P2

**Владельцы:** техлид + Jetty + Netty. **Статус:** слабое assertion подтверждено; дополнительные сценарии частично не проверены.

**Код:** TEST `:190–197`, `:257–260`.

`assertThrows(IOException)` принимает также `HttpTimeoutException`. Регрессия от своевременного обрыва к зависанию до client timeout может остаться зелёной. Дополнительный chunked-abort эксперимент при этом прошёл на текущей реализации.

**Действия:**

1. В truncation-тесте получить ожидаемый prefix и проверить оперативный обрыв; исключить timeout как допустимый успешный результат теста.
2. Добавить chunked response без завершающего чанка. Для close-delimited HTTP-ответа закрытие соединения само является нормальным EOF: не требовать обнаружения усечения, которое невозможно определить из framing.
3. Добавить HEAD/204/304/пустые ответы, ранний 413, Expect: 100-continue, обрыв downstream во время ответа.
4. Проверить request-side hop-by-hop заголовки и токены Connection, повторные end-to-end headers, POST без charset, compressed payload без распаковки, raw encoded path/query, отсутствие retry/redirect.
5. Контракт GET/HEAD body и framing взять из P-01, локальные ERROR — из P-02; не дублировать проверки в несвязанных наборах.

**Приёмка:** тесты различают корректный EOF, усечение, отказ, timeout и отмену. Для каждой новой проверки описан конкретный ошибочный вариант, который она обнаруживает.

## P-07. Параметризовать минимальные лимиты и таймауты — P2

**Владельцы:** Spring + техлид. **Статус:** подтверждённое ограничение сопровождаемости, не ошибка текущих defaults.

**Код:** PET `ProxyTransport.java:17–25`, `ProxyCommand.java:77`, `ProxyApplication.java:17`; `src/main/resources/application.yml:15`; TEST `:61`, `:170`, `:174`.

**Действия:**

1. Ввести небольшой валидируемый `@ConfigurationProperties("proxy")`: origin, admission/channel limits, connect/read/whole-exchange timeouts; pool/acquire настройки — только если выбран reuse/pool.
2. Разделить смысл общего deadline, включающего upload, и idle timeout. Явно определить связь ограничения каналов и admission limit. Настраивать прямой Netty transport, не Reactor Netty client.
3. Проверять origin и допустимый порт, положительные лимиты/интервалы до создания рабочих ресурсов.
4. Использовать короткие deadlines и необходимые лимиты в тестах вместо ожидания минуты и повторения магического 32.

**Приёмка:** неверная конфигурация не запускает приложение; overrides действуют без изменения Java; исходные defaults описаны; timeout/acquire/slow upload ветки имеют заданные исходы и корректный cleanup. Этот небольшой пункт можно выполнить раньше P-03 для подготовки детерминированных тестов.

## P-08. Измерить стоимость копирования ответа и flush — P2, необязательная оптимизация после корректности

**Владельцы:** Jetty + Netty. **Статус:** копирование и flush-per-chunk подтверждены; выигрыш альтернатив не измерен.

**Код:** PET `ProxyCommand.java:65–66`; REF `proxy/streaming/AsyncJettyBodyWriter.java:127`, `:166–195`.

Текущий bridge записывает direct ByteBuf через OutputStream с копированием через heap и вызывает `flushBuffer()` после каждого чанка. Исходный Jetty writer использует NIO ByteBuffer views и сигнал готовности, удерживая ByteBuf до завершения записи.

**План эксперимента:** сохранить понятный virtual-thread вариант как baseline; отдельно сравнить Jetty/Servlet ByteBuffer output или адаптацию исходного async writer. Проверять wrappers, readiness, lifetime буфера, slow-client поведение. Сравнить flush-per-chunk с ограниченным batching по throughput, аллокациям, числу записей и задержке первого байта.

**Условие внедрения:** измеренный полезный результат без ухудшения корректности и без потери ранней доставки response. Не переносить блокирующий fallback исходного writer на Netty event loop.

## P-09. Проверить вариант input через Servlet 6.1 ByteBuffer — P3, необязательный эксперимент

**Владельцы:** Jetty + Netty. **Статус:** API доступно и Jetty 12.1.4 его реализует; преимущество не измерено.

**Код:** PET `ProxyCommandSupport.java:24–26`.

Servlet 6.1 имеет `read(ByteBuffer)`, а Jetty HttpInput переопределяет его. Можно сравнить прямое заполнение NIO view direct ByteBuf с текущим heap-buffer вариантом. Это не устраняет копирование из буферов Jetty и не даёт абсолютного zero-copy.

**План и приёмка:** корректно обслужить position/limit, writerIndex, EOF, исключения и cancel; проверить обёрнутые ServletInputStream; измерить аллокации/throughput и сохранять простой вариант, если выгода не оправдывает усложнение.

## P-10. Уравнять контейнеры в тестовом и обычном runtime — P3

**Владельцы:** Spring. **Статус:** лишние зависимости подтверждены; текущие тесты действительно используют Jetty.

**Код:** `build.gradle:19`; `gradle.lockfile:57`, `:59`, `:135–142`.

Через тестовый starter добавляются Tomcat server jars, отсутствующие в обычном runtime. Это не означает, что восемь тестов работали на Tomcat: логи подтверждают Jetty.

**Действия:** исключить Tomcat server starter/runtime на тестовом пути, обновить lockfile, добавить явную проверку Jetty web-server factory. Не удалять `tomcat-embed-el` только из-за названия: EL implementation сам по себе не является вторым servlet container.

**Приёмка:** серверный runtime и тесты используют Jetty, test classpath не содержит лишнего Tomcat container.

## P-11. Описать границу интеграции с исходным MVC-приложением — P3

**Владельцы:** Spring + техлид. **Статус:** текущие Boot properties корректны; ограничение относится к переносу примера.

**Код:** `src/main/resources/application.yml:8–14`; PET `ProxyApplication.java:23`; REF `hosts/filter/ProxyAwareFormContentFilter.java:26`, `proxy/ProxySpringConfiguration.java:42–63`.

Глобальное отключение multipart/FormContentFilter и servlet `/*` подходят выделенному pet-proxy. В смешанном портале они меняют работу локальных MVC endpoints. В исходном модуле уже есть выборочный обход form-парсинга для proxy routes.

**Действия:** добавить короткий раздел README о переносе: выбор backend выполняется до consuming filters; сырой поток сохраняется только на proxy routes; локальные формы/multipart должны продолжать работать. Отдельный смешанный вариант с локальным MVC endpoint создавать только если он станет частью задачи.

**Приёмка:** документация явно отделяет выделенный proxy от смешанного приложения. Для возможного смешанного варианта — побайтные proxy form/multipart и работающий локальный парсинг.

## P-12. Согласовать документацию с фактическими гарантиями — P3

**Владельцы:** техлид; проверяют все эксперты. **Статус:** устаревший комментарий подтверждён, часть обещаний опровергнута P-01.

**Код:** PET `DemoBackend.java:40–41`; README: описание методов, памяти, capacity и очистки.

**Действия:** убрать устаревшее «поток передаёт Gateway»; после P-00 описать прямой Netty Channel/pipeline и роль Mono только в управлении командой. После P-01/P-04/P-05 обновить гарантии: поддержанные методы и framing, смысл semaphore, что действительно проверено по памяти/cancel. Сохранить различие между отсутствием полной буферизации и абсолютным zero-copy.

**Приёмка:** описание соответствует реализации и результатам проверок; README не заявляет непроверенный физический лимит ресурсов или отсутствие всех копий.

Эти находки фиксируются для понимания примера и будущих регрессий pet. План не поручает исправлять или собирать исходный модуль.

| ID | Наблюдение и подтверждение | Источник REF | Что сделать в рамках плана |
|---|---|---|---|
| L-01 | Полная агрегация, копирование heap→direct, затем возможное повторное кодирование формы/multipart — исходная мотивация, а не новая ошибка pet | `proxy/ProxyCommandSupport.java:77–81`, `:96–156`; `proxy/RequestBodyReader.java:30–36` | Сохранить byte-for-byte и streaming tests; не возвращать этот путь при исправлении P-01 |
| L-02 | При keepAlive=true фильтр оставляет только exact-case `Connection`, отбрасывая другие собранные заголовки; подтверждено кодом | `proxy/ProxyCommandSupport.java:231–235` | Отдельный потенциальный P1 backlog исходного модуля; в pet проверить Content-Type, Authorization, повторные headers и casing |

## Порядок реализации и критерии завершения

| Этап | Работы | Зависимости | Критерий перехода |
|---|---|---|---|
| 1. Контракт прямого Netty и регрессионные сценарии | Зафиксировать P-00; добавить проверки P-01/P-02; подготовить барьеры P-03; минимально параметризовать deadlines из P-07 | Нет | Границы transport/servlet bridge определены; тесты обнаруживают установленные дефекты |
| 2. Прямой транспорт и корректность ответа | Выполнить P-00 вместе с P-01; исправить P-02/P-03 | Этап 1 | Нет Reactor Netty в целевом транспорте; новые и исходные восемь тестов проходят; есть один terminal outcome |
| 3. Фактическое завершение и backpressure | P-04, P-05, P-06; закончить P-07 и P-10 | Этап 2 | Проверены I/O tasks, connections, buffers, read-ahead и shutdown; отсутствие timeout не подменяет корректный abort |
| 4. Документация и границы | P-11, P-12, сравнительное приложение | Полученные результаты предыдущих этапов | README соответствует реальному контракту; исходный модуль не изменён |
| 5. Необязательные измерения | P-08/P-09 | Корректный стабильный baseline | Оптимизации принимаются только при измеренной выгоде; отказ от усложнения допустим |

Netty и Spring могут параллельно подготовить регрессионные fixtures для P-01 и P-02. Изменения transport, `ProxyCommand` и `ProxyServlet` для P-00–P-03 согласовывает техлид, поскольку отправка, framing, ownership и terminal cleanup связаны. Не тратить отдельный этап на доведение Reactor Netty варианта: его выявленные дефекты используются для регрессий прямого Netty решения. Производительные ByteBuffer-пути не вводятся одновременно с исправлением lifecycle: сначала нужен проверенный baseline.

Завершение обязательной части: транспорт соответствует прямому io.netty исходного примера; P1 закрыты воспроизводимыми регрессиями; проверены завершение и потоковое давление в заявленном контракте; все ошибки имеют определённый terminal outcome; документация не обещает больше, чем проверено. Не требуется внедрять production-функции портала или безусловно выполнять необязательные оптимизации.
