# Бэкенды для проверки потоковой передачи и отказов

Набор локальных HTTP/1.1-серверов и клиентов для проверки Java-прокси настоящими
сетевыми соединениями. Нужен **Python 3.10 или новее**; сторонних библиотек нет.
Большие тела генерируются и проверяются порциями. Файлы на диске появляются
только при явном использовании `generate_file.py` или `--output`.

| Файл | Назначение |
|---|---|
| `streaming_backend.py` | Отправка виртуального файла и приём потока с вычислением длины и SHA-256 |
| `fault_backend.py` | Управляемые статусы, задержки, ранние ответы и обрывы |
| `streaming_client.py` | Загрузка/скачивание через прокси с проверкой полного содержимого |
| `generate_file.py` | Создание настоящего файла порциями для curl, multipart и других клиентов |
| `http_support.py` | Общий HTTP-адаптер, ограниченные чтения fixed/chunked и генератор данных |

По умолчанию оба сервера слушают только `127.0.0.1`, обслуживают до 32 соединений
одновременно и закрывают соединение после запроса. При превышении лимита
отвечают 503. Это инструменты локальной проверки, не production HTTP-серверы.
Размер прикладных порций ограничен; это не обещание zero-copy или предела памяти
всего процесса: свои буферы также имеют Python, Java, TLS и операционная система.

## Запуск нормального бэкенда и прокси

Во всех примерах ниже рабочая директория — корень **`streaming-proxy-pet`**,
не каталог `backend-emulators`. Java-приложению нужен JDK 21.

Сначала подготовьте дистрибутив:

```bash
./gradlew installDist
```

Терминал 1 — эмулятор больших потоков на порту 9090:

```bash
python3 backend-emulators/streaming_backend.py --port 9090
```

На этом порту не должен одновременно работать прежний `DemoBackend`.

Терминал 2 — Java-прокси на порту 8080, направленный к эмулятору:

```bash
BACKEND_URL=http://127.0.0.1:9090 PROXY_PORT=8080 \
  build/install/streaming-proxy-pet/bin/streaming-proxy-pet \
  --proxy.exchange-timeout=10m
```

Общий срок обмена включает загрузку клиентом. Для многогигабайтных передач и
искусственных пауз здесь он увеличен с обычных 60 секунд до 10 минут.
`--timeout` проверяющего Python-клиента задаёт срок **отдельной сетевой операции**,
а не всего обмена; это другой таймер.

Проверка доступности через прокси:

```bash
curl -sS http://127.0.0.1:8080/health
```

Для проверки самого эмулятора без прокси замените `--base-url` в командах клиента
на `http://127.0.0.1:9090`. Серверы останавливаются через Ctrl+C в своих терминалах.

## Передачи размером больше 1 GiB

`1 GB = 1 000 000 000` байт, `1 GiB = 1 073 741 824` байта. Число **1073741947**
ниже равно **1 GiB + 123 байта**, то есть строго больше и 1 GB, и 1 GiB.
Неполная последняя порция также проверяет обработку границы тела.

Следующие четыре команды выполняют большие передачи **по явному запросу**.
В обычный быстрый набор тестов гигабайтные тела не включены.

```bash
# Upload с известной длиной: Content-Length, метод PUT.
python3 backend-emulators/streaming_client.py upload \
  --base-url http://127.0.0.1:8080 --method PUT \
  --size 1073741947 --framing fixed --chunk-size 64KiB --timeout 600

# Upload без Content-Length: HTTP chunked, метод DELETE.
python3 backend-emulators/streaming_client.py upload \
  --base-url http://127.0.0.1:8080 --method DELETE \
  --size 1073741947 --framing chunked --chunk-size 64KiB --timeout 600

# Download с Content-Length.
python3 backend-emulators/streaming_client.py download \
  --base-url http://127.0.0.1:8080 \
  --size 1073741947 --framing fixed --chunk-size 64KiB --timeout 600

# Download без заранее указанной длины, с завершающим HTTP-чанком.
python3 backend-emulators/streaming_client.py download \
  --base-url http://127.0.0.1:8080 \
  --size 1073741947 --framing chunked --chunk-size 64KiB --timeout 600
```

Успех означает exit code 0 и JSON с `bytes`, `sha256`, `status`, длительностью
и диагностической скоростью. При upload длина и SHA-256 сверяются с ответом
бэкенда; при download каждая порция сверяется с ожидаемым шаблоном по смещению,
после чего проверяется общая длина. Байт с номером N равен `N % 256`.
Обрезанный или изменённый поток не считается успешным. Шаблон повторяется каждые
256 байт: перестановку одинаковых 256-байтовых блоков такая проверка не различает.
Это проверка ожидаемых байтов, длины и хеша, а не гарантия обнаружить любую
перестановку логических блоков.

По умолчанию клиент генерирует/скачивает 1 GiB, использует порции 64 KiB,
`fixed` и адрес прокси 8080. Допустимы размеры в байтах, `KiB/MiB/GiB` и
`KB/MB/GB`; дробные значения не поддерживаются. Порция может иметь размер
от 1 байта до 1 MiB. Для upload доступны POST, PUT, PATCH, GET, DELETE и OPTIONS;
HEAD намеренно отсутствует в проверяющем клиенте, поскольку не возвращает JSON
с контрольной суммой. Сам `/upload` принимает тела основных HTTP-методов без
разбора form/multipart.

## Медленные стороны и ограничение чтения

Для первых опытов удобно взять 64 MiB, а не гигабайт. Пауза применяется после
каждой порции, поэтому её суммарное время зависит от `--chunk-size`.

```bash
# Бэкенд медленно читает upload: прокси должен перестать опережать потребителя.
python3 backend-emulators/streaming_client.py upload \
  --size 64MiB --framing chunked --server-delay-ms 5 --timeout 600

# Клиент медленно читает download: должен замедлиться и отправляющий бэкенд.
python3 backend-emulators/streaming_client.py download \
  --size 64MiB --framing chunked --pause-ms 5 --timeout 600

# Бэкенд отдаёт ответ небольшими порциями с паузой между ними.
python3 backend-emulators/streaming_client.py download \
  --size 64MiB --chunk-size 16KiB --server-delay-ms 2 --timeout 600

# Клиент медленно отправляет запрос.
python3 backend-emulators/streaming_client.py upload \
  --size 64MiB --chunk-size 16KiB --pause-ms 2 --timeout 600
```

`--pause-ms` задерживает клиентское чтение или генерацию upload; `--server-delay-ms`
задерживает чтение или запись бэкенда. В серверном URL этим параметрам соответствуют
`chunk` и `delay_ms`. Например:

```bash
curl -sS -o /dev/null \
  'http://127.0.0.1:8080/download?size=64MiB&framing=chunked&chunk=16KiB&delay_ms=2'
```

Наблюдение скорости и RSS полезно для диагностики. Один такой запуск не является
сравнительным throughput/CPU/GC-бенчмарком: на результат влияют генерация шаблона,
проверка SHA-256, несколько процессов, сеть, JVM и размер порций. Отсутствие
роста памяти до размера файла также не доказывает абсолютный минимум копий.

## Файл на диске и curl

Создать настоящий файл больше 1 GiB можно явно:

```bash
python3 backend-emulators/generate_file.py /tmp/proxy-large.bin \
  --size 1073741947 --chunk-size 64KiB
```

Он займёт указанный объём на диске. Генератор печатает длину и SHA-256 и по умолчанию
отказывается заменять существующий файл; для намеренной замены есть `--overwrite`.
При прерывании может остаться частичный файл.

Для потоковой отправки файла через curl используйте upload-режим:

```bash
# Обычный файл: curl знает его длину и отправляет Content-Length.
# По умолчанию используется PUT; /upload возвращает JSON с длиной и SHA-256.
curl -sS --max-time 600 -T /tmp/proxy-large.bin http://127.0.0.1:8080/upload

# Stdin: длина заранее неизвестна, явно используем HTTP/1.1 chunked.
curl -sS --http1.1 --max-time 600 --upload-file - \
  -H 'Transfer-Encoding: chunked' http://127.0.0.1:8080/upload \
  < /tmp/proxy-large.bin
```

Не используйте `curl --data-binary @file` как доказательство ограниченного
потребления памяти клиентом: такой режим может предварительно прочитать файл
целиком. Для больших потоков подходят `streaming_client.py` или `curl -T`.

Чтобы сохранить скачанный поток, добавьте клиенту `--output`:

```bash
python3 backend-emulators/streaming_client.py download \
  --size 1073741947 --framing chunked --timeout 600 \
  --output /tmp/proxy-downloaded.bin
```

Существующий файл защищён от замены; разрешение задаётся отдельным `--overwrite`.
При ошибке частичный файл остаётся для диагностики, но клиент завершается с
ненулевым кодом. Без `--output` download не создаёт файла.

## Отдельный бэкенд отказов

Для быстрых сценариев отказов используются другие порты и короткие таймауты.
Обычный прокси 8080 с десятиминутным сроком можно оставить работающим.

Терминал 3 — бэкенд отказов:

```bash
python3 backend-emulators/fault_backend.py --port 9091
```

Терминал 4 — второй Java-прокси:

```bash
BACKEND_URL=http://127.0.0.1:9091 PROXY_PORT=8081 \
  build/install/streaming-proxy-pet/bin/streaming-proxy-pet \
  --proxy.read-timeout=2s --proxy.exchange-timeout=5s
```

| Маршрут бэкенда | Сценарий и ожидаемый результат через прокси 8081 |
|---|---|
| `/status?code=503` | Обычный окончательный статус origin. Клиент должен получить 503, а не новую транспортную ошибку |
| `/early-response?code=413` | Финальный ответ без чтения request body. Прокси сохраняет 413 и останавливает upload |
| `/delay?seconds=10` | Задержка до отправки заголовков. Короткий proxy timeout должен дать 504 |
| `/stall?seconds=10&after=16KiB` | Сначала 200 и префикс, затем пауза. После timeout уже начатый ответ обрывается; второй 502/504 к нему не дописывается |
| `/truncate?size=1GiB&after=128KiB&framing=fixed` | Обещана большая Content-Length, отправлен только префикс. Клиент должен обнаружить недостающие байты |
| `/truncate?size=1GiB&after=128KiB&framing=chunked` | Отправлен префикс без завершающего нулевого чанка. Это некорректный конец ответа |
| `/disconnect` | Соединение закрывается до HTTP-статуса. Прокси должен вернуть 502 |
| `/redirect` | 302 с Location `/health`. Прокси сам не следует перенаправлению |
| `/headers` | Два Set-Cookie и X-Backend должны сохраниться; Connection-опция X-Hop-Only и одноимённый заголовок должны быть удалены |

Примеры коротких проверок:

```bash
curl -sS --max-time 10 -i 'http://127.0.0.1:8081/status?code=503'
curl -sS --max-time 10 -i 'http://127.0.0.1:8081/delay?seconds=10'
curl -sS --max-time 10 -i http://127.0.0.1:8081/disconnect
curl -sS --max-time 10 -i http://127.0.0.1:8081/redirect
curl -sS --max-time 10 -i http://127.0.0.1:8081/headers

# Тело ответа отбрасывается, заголовки остаются видны.
# Для этих трёх команд ожидается ошибка передачи после HTTP 200.
curl -sS --max-time 10 -D - -o /dev/null \
  'http://127.0.0.1:8081/stall?seconds=10&after=16KiB'
curl -sS --max-time 10 -D - -o /dev/null \
  'http://127.0.0.1:8081/truncate?size=1GiB&after=128KiB&framing=fixed'
curl -sS --max-time 10 -D - -o /dev/null \
  'http://127.0.0.1:8081/truncate?size=1GiB&after=128KiB&framing=chunked'
```

Здесь намеренно нет `curl --fail`: полученный HTTP 503 или 504 — самостоятельный
ожидаемый результат, при котором curl может вернуть 0. Для stall/truncate важен
ненулевой код **ошибки передачи**, а не просто показанный статус 200.
Код curl 28 означает, что истёк срок самого клиента; это не доказательство
корректного обрыва прокси. `--max-time 10` выбран больше сроков прокси 2/5 секунд,
чтобы различать эти исходы. Для redirect не добавляйте `-L`, если проверяется
отсутствие автоматического следования.

Ранний ответ с `Expect: 100-continue`:

```bash
# Прямой бэкенд отвечает окончательным 413 ещё при разборе заголовков,
# не отправляя предварительного 100 Continue и не читая тело.
curl -sS --max-time 10 -i -H 'Expect: 100-continue' \
  --data-binary 'small fixture' 'http://127.0.0.1:9091/early-response?code=413'

# Через Java-прокси проверяем сохранение окончательного ответа origin.
curl -sS --max-time 10 -i -H 'Expect: 100-continue' \
  --data-binary 'small fixture' 'http://127.0.0.1:8081/early-response?code=413'
```

JSON содержит `request_body_read: false`. При запросе через прокси промежуточный
100 Continue клиенту может сформировать Jetty; это отдельное соединение и не
означает, что fault-бэкенд начал читать тело. `streaming_client.py` предназначен
для полной успешной передачи на `/upload` и `/download`; его не следует использовать
как универсальный клиент ранних отказов.

## Параметры серверов

Оба сервера принимают `--host`, `--port`, `--chunk-size`, `--io-timeout`,
`--max-connections` и `--quiet`. По умолчанию: loopback, порция 64 KiB,
30 секунд на отдельную операцию сокета и 32 обслуживаемых соединения.
`--quiet` отключает журнал отдельных запросов. Порт 0 выбирает свободный порт;
фактический адрес печатается при старте в JSON.

`/download` по умолчанию генерирует 1 GiB; query-параметры `size`, `framing`,
`chunk`, `delay_ms` меняют размер, framing, порцию и паузу. HEAD сообщает только
метаданные и не генерирует многогигабайтное тело. `/upload` принимает raw body
с Content-Length либо chunked и возвращает JSON с длиной, SHA-256, методом,
исходным target и Content-Type. Форма, multipart и сжатое содержимое не разбираются.

## Автоматические и выполненные ручные проверки

Быстрые тесты запускаются из каталога эмуляторов:

```bash
cd backend-emulators
python3 -m unittest discover -v
```

Они используют небольшие данные и локальные порты; гигабайтные передачи остаются
явной ручной проверкой командами выше. CLI каждого скрипта доступен через `--help`.

Через собранный Java-прокси выполнены четыре передачи по **1 073 741 947 байт**:

| Направление | Framing | Метод | Результат | Наблюдавшееся время |
|---|---|---|---|---|
| Upload | fixed | PUT | HTTP 200, длина и SHA-256 совпали | 6,287 с |
| Upload | chunked | DELETE | HTTP 200, длина и SHA-256 совпали | 7,998 с |
| Download | fixed | GET | HTTP 200, все порции и длина проверены | 3,780 с |
| Download | chunked | GET | HTTP 200, все порции и длина проверены | 4,828 с |

Всего передано **4 294 967 788 байт**, больше 4 GiB. Данные генерировались и
отбрасывались без создания гигабайтных файлов. Для всех четырёх потоков получен
одинаковый SHA-256:

```text
25c99c1c4a4ff7f4fe8e0c10bf573a3433482c5e619f40f8595ea97451aff2f4
```

В этом запуске выборочно наблюдались пиковые RSS: эмулятор 14,96 MiB, проверяющий
клиент 16,15 MiB, Java-прокси 244,64 MiB. JVM запускалась с
`-Xms64m -Xmx256m -XX:MaxDirectMemorySize=128m`. Это наблюдения одного запуска,
а не гарантированные пределы RSS и не сравнительный benchmark. Heap/direct limits
JVM не включают всю память процесса; интервальное измерение может пропустить пик.
Данные запуска: `build/emulator-validation/large-streams.json` относительно корня
pet-проекта.

Итоговый быстрый набор: **24 теста прошли** — 16 сценариев серверов и 8 проверок
клиента/генератора; `python3 -m unittest discover -v` завершился успешно примерно
за 1,3 с. Гигабайтные передачи в этот набор не входят.

Дополнительно через настоящий Java-прокси прошли **9 сценариев отказов и
HTTP-поведения**: 503 origin; 302 без следования; два Set-Cookie с удалением
hop-by-hop заголовка; 502 при disconnect; 504 при задержке до заголовков;
обрыв fixed и chunked ответа после 16 385 байт; 200 с префиксом и последующим
обрывом при stall; ранний 413 до отправки клиентом тела с объявленной длиной
1 GiB. Ошибки незавершённого ответа были отличены от timeout самого клиента.
При остановке проверенного Java-прокси не было зависания graceful shutdown.
